## 경쟁 서비스 가정부터 수정해야 합니다

현재 정리된 경쟁 분석에는 위험한 부분이 있습니다.

- Partiful은 이미 날짜 투표, 식이 제한·장소 선호 질문, Google·Apple·Outlook 캘린더 동기화를 제공합니다. 따라서 단순히 “캘린더 연동”만으로는 차별화가 아닙니다. 차별점은 **참가자의 Free/Busy를 읽고 자동으로 시간을 결정하는 인바운드 연동**이어야 합니다. Partiful 공식 기능, Partiful 도움말
- Google AI Mode의 식당 예약 기능도 더 이상 “아직 미출시”라고 표현하면 안 됩니다. 2025년부터 미국을 시작으로 실제 배포됐고, 조건에 맞는 실시간 예약 가능 식당을 찾아 예약 페이지까지 연결합니다. 다만 사용자가 최종 예약 단계를 수행한다는 점은 여전히 차별화 여지가 있습니다. Google 공식 발표
- 일정 분야에는 캘린더 Free/Busy를 읽고 공통 시간을 계산한 뒤 이벤트까지 생성하는 서비스도 이미 있습니다. 즉 **일정 자동화 + 캘린더 생성**만으로도 부족합니다. WhenMeet.me 공식 설명

결국 차별화는 기능의 존재가 아니라 다음 세 가지 조합에서 나와야 합니다.

1. 여러 사람의 시간·알레르기·예산·거리·취향을 동시에 조정한다.
2. 평균 취향이 아니라 소외되는 사람이 없도록 공정하게 결정한다.
3. 승인 후 예약과 일정 생성을 트랜잭션처럼 실행하고 실패를 복구한다.

## 반대편 심사위원의 “왜?”

### “왜 카카오톡 투표나 Partiful이면 안 되죠?”

투표는 정보를 모을 뿐, 최종 결정을 다시 총무에게 넘깁니다. 이 서비스는 조건을 계산하고 승인 후 실행까지 해야 합니다.

단, 실제 시연에서 총무의 행동이 줄어드는 것을 보여주지 못하면 이 답변은 성립하지 않습니다.

### “왜 AI여야 하죠? 필터 몇 개면 되는 것 아닌가요?”

맞는 지적입니다. 모든 판단을 LLM에 맡기면 오히려 기술적으로 약해 보입니다.

- LLM: 자연어를 시간·예산·지역·음식 등의 구조화된 조건으로 변환
- 제약조건 엔진: 가능한 시간과 식당을 정확하게 계산
- LLM: 결과와 타협 이유를 자연어로 설명
- 에이전트: 승인 후 예약·캘린더 도구 실행

이 역할 분리가 있어야 “AI를 붙인 필터 서비스”라는 공격을 피할 수 있습니다.

### “왜 모든 참가자가 캘린더 권한을 줘야 하죠?”

전원 가입과 권한 허용을 전제로 하면 서비스가 실패합니다.

- 연결한 사용자는 일정 제목이 아닌 Free/Busy만 제공
- 연결하지 않은 사용자는 링크에서 가능한 시간만 선택
- 참가자는 가입 없이 응답 가능

이 혼합 방식이 필요합니다.

### “왜 밸런스 게임을 먼저 해야 하죠?”

현재로서는 핵심 기능이 아닙니다. 재미는 있지만 가입 마찰과 구현량을 늘리고, 일회성 모임에는 효용이 작습니다.

**2일 MVP에서는 제외**하고, 모임별로 알레르기·못 먹는 음식·선호 메뉴만 30초 안에 입력하게 하는 편이 낫습니다. 장기적인 반복 사용 기능으로 백로그에 두십시오.

### “예약까지 자동 완료된다는 것을 정말 증명할 수 있나요?”

가장 위험한 질문입니다. 식당 검색보다 실제 예약 API 확보가 훨씬 어렵습니다.

첫날 오전까지 다음 중 하나를 확정해야 합니다.

- 실제 예약 API 또는 샌드박스 확보
- 예약 가능한 제휴 식당을 제한하고 자체 예약 콘솔 구현
- 실제 예약 요청 전송까지만 수행하고, 이를 “예약 완료”라고 과장하지 않기

브라우저 자동화로 외부 예약 사이트를 조작하는 방식은 로그인·캡차·약관·UI 변경 때문에 시연 위험이 큽니다.

### “모두가 가능한 시간이 없으면 AI는 무엇을 하나요?”

“가능한 일정이 없습니다”로 끝나면 에이전트 가치가 없습니다.

> “화요일에는 1명만 불가능하고, 목요일에는 식당 예산이 10% 초과합니다. 어떤 조건을 완화할까요?”
> 

처럼 **가장 적은 희생으로 완화할 조건을 제시**해야 합니다. 이 부분이 좋은 기술 차별점이 됩니다.

## 2일 MVP 범위

핵심 기능은 두 개로 압축하십시오.

### 1. 모임 조건 조율 엔진

- 총무의 자연어 입력
- 참가자 링크 공유
- 캘린더 Free/Busy 또는 수동 가능 시간 수집
- 알레르기·예산·이동거리 등 하드 조건 적용
- 선호도 등 소프트 조건으로 후보 순위 계산
- 선택 이유와 제외 이유 설명

### 2. 승인 후 실행 에이전트

- 실행 전 예약 내용과 취소 조건 미리보기
- 총무 승인
- 예약 생성
- 캘린더 이벤트 및 초대 생성
- 실행 기록 표시
- 실패 시 안전한 재시도 또는 취소

성공 흐름은 하나면 충분합니다.

> 회식 조건 입력 → 5명의 일정·제약 수집 → 시간/식당 하나 확정 → 승인 → 예약 생성 → 전원 캘린더 등록
> 

결제, 단체 채팅, 비용 정산, 장기 취향 학습, 여러 캘린더 사업자 지원, 웨딩·친목·여행 등 범용화는 모두 후순위입니다.

## 추천 기술 구성

- 프런트·서버: Next.js 단일 프로젝트
- 데이터: Supabase/PostgreSQL
- 일정: Google Calendar OAuth, FreeBusy, Event 생성
- 장소: 지도·로컬 검색 API 한 종류
- AI: 자연어를 고정 JSON 스키마로 변환하고 도구 실행
- 추천: 결정론적 제약조건 및 점수 계산
- 예약: `booking adapter` 인터페이스와 한 개의 실제 성공 경로
- 안전장치: 승인 상태, 중복 예약 방지 키, 실행 로그, 재시도

상태도 명확히 두는 것이 좋습니다.

`조건 수집 → 후보 계산 → 승인 대기 → 예약 완료 → 캘린더 생성 → 실행 기록`

## 다음 세션에서 반드시 확정할 것

칠판에서는 기능 이름만 나열하지 말고, 각 기능에 네 가지를 적으십시오.

- 사용자가 무엇을 입력하는가
- AI가 무엇을 판단하는가
- 실제로 어떤 상태가 바뀌는가
- 실패하면 어떻게 복구하는가

우선순위 기준은 단순합니다.

> **핵심 시연 기여도 × 심사 점수 기여도 × 구현 확실성 ÷ 실패 위험**
> 

그리고 첫날 오전에 세 가지를 직접 검증해야 합니다.

1. Google Calendar에서 실제 Free/Busy 조회와 이벤트 생성
2. 예약 생성 및 취소 경로
3. 5명 시나리오가 10회 연속 안정적으로 시연되는지

기대효과는 아직 실적처럼 쓰지 말고 목표치로 제시하십시오.

- 모임 확정 시간 3분 이내
- 총무의 주요 조작 2회: 조건 입력과 승인
- 참가자 응답 30초 이내
- 예약·캘린더 실행 성공률 100%로 시연
- 모든 외부 실행에 기록과 재시도 제공

최종적으로 이 프로젝트의 경쟁 상대는 Partiful이나 Google 자체가 아닙니다. **“결국 총무가 마지막 결정을 하고 예약해야 하는 상태”**가 경쟁 상대입니다. 이 마지막 수고를 실제로 없애는 데 성공하면 주제와 심사 기준 모두에 강하게 부합합니다.

## AI 기획 구체화 조언

- 전문
    
    현재 기획에서 더 필요한 것은 기능 추가보다 **모호한 부분을 결정 가능한 수준으로 구체화하는 것**입니다. 특히 아래 네 가지가 비어 있습니다.
    
    > 누가 쓰는가 → AI가 어떻게 결정하는가 → 실제 무엇을 실행하는가 → 2일 안에 어디까지 증명하는가
    > 
    
    ## 1. 첫 타깃과 상황 좁히기
    
    “모든 모임”은 너무 넓습니다. 회식, 청첩장 모임, 친구 약속은 참여 방식과 예산, 예약 기준이 전부 다릅니다.
    
    MVP 타깃은 다음처럼 좁히는 것을 권합니다.
    
    > **서울에서 4~8명의 직장인 회식을 준비하는 총무**
    > 
    
    이 타깃이 좋은 이유는 다음과 같습니다.
    
    - 반복적으로 발생한다.
    - 회사 캘린더를 사용할 가능성이 높다.
    - 인원, 예산, 위치 등의 조건이 명확하다.
    - 일정 확정 후 식당 예약이라는 실행이 반드시 발생한다.
    - 전후 시간 절약을 측정하기 쉽다.
    
    이후 친구 모임, 청첩장 모임 등으로 확장하면 됩니다.
    
    ## 2. 핵심 문제를 수치로 검증하기
    
    “약속 조율이 번거롭다”는 공감은 되지만 심사위원에게는 약합니다. 무엇이 얼마나 불편한지 확인해야 합니다.
    
    최소 5명에게 다음을 인터뷰해보세요.
    
    - 최근 단체 약속을 잡을 때 메시지를 몇 번 주고받았는가?
    - 일정 확정까지 얼마나 걸렸는가?
    - 가장 힘든 단계는 시간, 장소, 메뉴, 예약 중 무엇인가?
    - 참가자들이 캘린더 연결을 허용할 것 같은가?
    - 자동 예약 전에 반드시 확인하고 싶은 것은 무엇인가?
    - 이런 서비스가 있어도 결국 직접 확인할 부분은 무엇인가?
    
    그 결과로 문제를 다음처럼 구체화해야 합니다.
    
    > “6명 회식을 준비하는 총무가 일정과 식당을 확정하기 위해 평균 ○분 동안 ○회의 메시지를 주고받는다.”
    > 
    
    숫자는 추측하지 말고 인터뷰 결과로 채워야 합니다.
    
    ## 3. 전체 사용자 흐름 확정하기
    
    현재는 기능 목록은 있지만 참가자가 어떻게 참여하는지가 불분명합니다. 한 개의 성공 경로를 화면 단위로 확정해야 합니다.
    
    1. 총무가 자연어로 조건을 입력한다.
    2. 참가자에게 응답 링크를 보낸다.
    3. 참가자는 캘린더를 연결하거나 가능한 시간을 직접 선택한다.
    4. 참가자는 알레르기·못 먹는 음식·예산 조건을 입력한다.
    5. AI가 시간과 식당 후보를 계산한다.
    6. 총무가 최종 실행 내용을 확인하고 승인한다.
    7. 예약을 생성하고 전원 캘린더에 일정을 등록한다.
    8. 실행 결과와 취소·재시도 버튼을 보여준다.
    
    특히 다음을 결정해야 합니다.
    
    - 참가자도 가입해야 하는가?
    - 캘린더를 연결하지 않으면 어떻게 참여하는가?
    - 몇 명이 응답해야 계산을 시작하는가?
    - 응답하지 않은 사람은 어떻게 처리하는가?
    - 예약 후 인원이 변경되면 어떻게 되는가?
    
    ## 4. AI의 의사결정 기준 만들기
    
    “AI가 알아서 정한다”는 설명으로는 기술성을 인정받기 어렵습니다. 조건을 세 종류로 나누는 것이 좋습니다.
    
    ### 반드시 지켜야 하는 조건
    
    - 전원이 가능한 시간
    - 알레르기와 식이 제한
    - 식당 수용 인원
    - 영업시간
    - 최대 예산
    - 예약 가능 여부
    
    ### 가능하면 만족하는 조건
    
    - 선호 음식
    - 분위기
    - 이동거리
    - 특정 참가자의 선호
    - 리뷰와 평점
    
    ### 모임 목적에 따른 조건
    
    - “누군가의 송별회이므로 해당 인물의 선호 우선”
    - “특정 장소 방문이 목적이므로 장소 고정”
    - “회식이므로 회사와의 거리 우선”
    
    후보가 없을 때의 행동도 핵심입니다.
    
    > “모든 조건을 만족하는 결과는 없습니다. 예산을 5천 원 올리면 3개, 반경을 1km 넓히면 5개의 후보가 생깁니다.”
    > 
    
    이런 **최소 조건 완화 제안**이 단순 추천 서비스와 차별화될 수 있습니다.
    
    ## 5. AI와 일반 알고리즘의 역할 분리하기
    
    기술 설계는 다음처럼 정리하는 것이 설득력 있습니다.
    
    - LLM: 자연어를 시간·예산·인원·지역 등 구조화된 조건으로 변환
    - 캘린더 API: 참가자의 가능한 시간 조회
    - 장소 API: 식당과 영업 정보 조회
    - 제약조건 엔진: 불가능한 후보 제거
    - 점수 계산: 남은 후보의 순위 결정
    - LLM: 선택 이유와 타협점을 설명
    - 실행 에이전트: 승인 후 예약과 캘린더 등록
    
    “LLM이 모든 것을 판단한다”보다 정확성, 재현성, 기술 적절성 측면에서 높은 평가를 받을 수 있습니다.
    
    ## 6. ‘자동 예약’의 정확한 의미 결정하기
    
    가장 먼저 검증해야 할 부분입니다.
    
    다음 세 표현은 완전히 다릅니다.
    
    - 예약 가능한 식당을 추천한다.
    - 예약 페이지까지 이동시킨다.
    - 사용자를 대신해 예약을 확정한다.
    
    서비스가 마지막을 주장하려면 실제 예약 성공을 증명해야 합니다. 따라서 첫날 오전까지 다음 중 하나를 선택해야 합니다.
    
    - 사용할 수 있는 실제 예약 API 확보
    - 특정 제휴 식당만 지원하는 자체 예약 시스템 구현
    - 식당 관리자용 간단한 예약 확인 화면 구현
    - 예약 요청까지만 전송하고 서비스 표현도 “예약 요청 완료”로 제한
    
    외부 예약이 불가능하다면 최소한 **Google Calendar 일정 생성은 실제로 동작**해야 합니다. 모의 예약을 실제 예약인 것처럼 발표하면 큰 감점 요소가 됩니다.
    
    ## 7. 신뢰와 안전장치 설계하기
    
    AI가 예약을 잘못하면 비용과 관계 문제가 생깁니다. 다음 항목이 필요합니다.
    
    - 실행 전 날짜·시간·인원·가격·취소 규정 미리보기
    - 사용자 명시적 승인
    - 중복 예약 방지
    - 예약 및 캘린더 생성 기록
    - 일부 단계 실패 시 재시도
    - 예약 취소 또는 일정 변경
    - 캘린더에서는 일정 제목이 아닌 Free/Busy만 조회
    - 캘린더 미연결 참가자를 위한 수동 입력 방식
    
    이 부분은 에이전트 서비스의 완성도를 보여주는 좋은 발표 요소입니다.
    
    ## 8. 기능 범위 나누기
    
    ### P0: 반드시 구현
    
    - 총무의 자연어 조건 입력
    - 참가자 응답 링크
    - 일정·식이 제한·예산 수집
    - 후보 계산과 선택 이유
    - 실행 전 미리보기와 승인
    - 실제 캘린더 이벤트 생성
    - 한 가지 예약 성공 경로
    - 실행 기록과 재시도
    
    ### P1: 시간이 남으면 구현
    
    - 개인 취향 저장
    - 이전 모임 기반 추천
    - 알림
    - 조건 완화 대화
    - 예약 변경·취소
    
    ### MVP에서 제외
    
    - 가입 시 밸런스 게임
    - 비용 정산
    - 단체 채팅
    - 사진 공유
    - 모든 캘린더 지원
    - 모든 예약 플랫폼 연동
    - 회식·친구·웨딩 등 모든 모임 유형 지원

    ## 9. 성공 지표 정의하기
