# AI 설계 핵심 정리

이 문서는 API 명세서가 아니라 **AI 파이프라인에서 무슨 문제를 발견했고 어떤 기준으로 설계했는지**를 정리한 자료다. 발표는 끝났고 지금은 프로젝트 정리용으로 핵심만 남긴다. 실제 Back↔AI 요청·응답 계약은 [`api-design2-backend.md`](api-design2-backend.md)를 기준으로 한다.

세 가지 핵심 주제는 다음과 같다.

1. **카테고리 사전 구성과 의미 기반 매핑** — 자유로운 자연어를 안정적인 서비스 코드로 바꾸는 방법
2. **참여자별 만족도와 공정성 점수** — 다수의 평균뿐 아니라 가장 불리한 참여자까지 고려하는 방법
3. **웹 검색 기반 영업시간 검증** — 장소가 실제 모임 시간에 영업하는지 외부 근거로 확인하는 방법

---

## 1. 카테고리 사전 구성과 의미 기반 매핑

### 문제

"연어 좋아해", "사시미 괜찮아", "회 종류는 다 좋아해"는 같은 의미지만 원문 그대로 저장하면 같은 선호로 묶어 조회·갱신·비교할 수 없다. 반대로 LLM에게 카테고리 이름까지 자유롭게 만들게 하면 `SALMON`/`SALMON_FOOD`/`RAW_SALMON`처럼 매번 다른 코드가 나와 DB 외래키로 쓸 안정적인 값이 안 된다.

### 검토한 방식과 선택

| 방식 | 한계 |
| --- | --- |
| 사용자 원문만 저장 | 같은 의미를 집계·비교·갱신하기 어려움 |
| 임베딩 + 코사인 유사도 | 문장을 벡터 하나로 압축해 "해산물은 별론데 조개는 좋아" 같은 반대 선호가 분리 안 됨 |
| 키워드/규칙 매칭 | 부정문·복합문·신조어가 늘수록 규칙이 기하급수적으로 복잡해짐 |
| LLM이 카테고리도 자유 생성 | 저장 코드가 흔들려 DB·Back·Front 계약을 보장 못함 |
| **고정 Vocabulary + LLM 의미 판단(채택)** | 의미 판단은 여전히 LLM 품질에 의존 |

음식·활동·분위기·음료 4개 도메인에 320개 코드(FOOD 200/ACTIVITY 50/MOOD 50/DRINK 20)로 계층형 사전을 만들고, 이 목록 전체를 프롬프트에 텍스트로 넣어 LLM이 문맥으로 판단하게 했다. **임베딩·벡터DB·코사인 유사도는 쓰지 않는다.** 이유:

1. **부정·복합문**: "해산물은 별로인데 조개는 좋아" 같은 문장에서 두 선호를 따로 뽑아낼 수 있다.
2. **강도·감정 판단**: `STRONG`/`WEAK` 구분은 문장을 이해해야 나온다.
3. **"부재 확인"**: `GENERALIZED`(사슴고기→육류)로 일반화해도 되는지 판단하려면 "더 구체적인 코드가 사전에 없다"를 확인해야 하는데, 목록 전체를 한 번에 보여주기 때문에 가능하다.
4. **인프라 단순함**: 현재 규모(320개, 약 6,700토큰)에서는 벡터 인프라 없이 프롬프트 하나로 끝난다.

### 핵심 메커니즘

```
FOOD
├─ SEAFOOD (해산물)
│  ├─ RAW_FISH (회) └─ SALMON (연어)
│  └─ SHELLFISH (조개류)
└─ KOREAN_FOOD (한식) └─ SAMGYEOPSAL (삼겹살)
```

LLM은 매핑 결과를 세 가지 중 하나로 낸다.

- **EXACT** — "연어 좋아해" → `SALMON` (직접 대응)
- **GENERALIZED** — 정확한 코드는 없지만 안전한 상위 범주가 있을 때(`VENISON` 없으면 `MEAT`로), 원문은 `rawValue`에 보존
- **UNMAPPED** — 억지로 묶으면 의미가 왜곡될 때("고수" → `VEGETABLE`은 채소 전체를 싫어한다는 뜻이 되므로 코드 없이 원문만 반환)

**안전장치**: LLM이 사전에 없는 코드를 만들어도 서버가 응답을 받자마자 실제 Vocabulary와 대조해 미등록 코드는 전부 `UNMAPPED`/`null`로 강제 정규화한다. 표시명·domain도 LLM이 아니라 서버가 검증된 코드 기준으로 원본 사전에서 다시 붙인다. 초기 구현은 320개 전체를 Gemini 구조화 출력의 `Literal` enum으로도 넣었지만, 의미 판단용 목록(프롬프트)과 모델 스키마의 역할을 분리해 `str | null`로 받고 서버가 allowlist 검증하는 방식으로 바꿨다.

계층 구조 덕분에 "해산물은 별로지만 조개는 좋아" 같은 문장을 `SEAFOOD/NEGATIVE`(넓은 비선호) + `SHELLFISH/POSITIVE`(구체적 예외)로 따로 보존할 수 있다.

### 한계

- 의미 매핑 정확도는 아직 실제 사용자 발화 데이터셋으로 정량 검증하지 않았다(현재 테스트는 mock LLM 응답 기준).
- `parentCode`는 강제 규칙이 아니라 LLM의 힌트라 실제 상위 범주가 맞는지 서버가 검증하지 않는다.
- Vocabulary 조회가 실패하면 모든 code가 `UNMAPPED`가 되는데, 이게 "매핑 불가"인지 "조회 장애"인지 구분되지 않는다.
- 캐시 갱신 정책(TTL/버전)이 없어 Back이 사전을 바꿔도 실행 중인 프로세스는 예전 목록을 계속 쓸 수 있다.
- 320개는 사용자 코퍼스로 검증한 완성 taxonomy가 아니라 제품 가설 기반으로 사람이 구성한 초기 seed다.

**사전 크기와 프롬프트 비용** (Gemini 토크나이저로 실측, `data/vocabulary_seed.sql` 기준):

| 항목 수 | 토큰 수 |
| --- | ---: |
| 50개 | 약 986 |
| 100개 | 약 2,113 |
| 200개 | 약 4,231 |
| 320개(전체) | 약 6,728 |

항목 수에 거의 정비례하지만 절대량은 Gemini 컨텍스트 윈도우의 1%도 안 된다. 진짜 비용은 "시끄러운 곳 싫어요"처럼 사전과 무관한 입력에도 매번 전체 텍스트를 다시 보낸다는 지연·비용 낭비 쪽이다. 사전이 더 커지면 1차 domain 분류 → 2차 leaf 후보 제공의 2단계 구조나, 후보 축소용 임베딩 검색을 검토할 수 있다(최종 코드 선택·allowlist 검증은 유지).

### 코드 근거

- Vocabulary seed와 계층: `data/vocabulary_seed.sql`
- Back Vocabulary 조회·캐시: `app/services/vocabulary_client.py`

- 테스트: `tests/graph/test_preference_extractor.py`, `tests/graph/test_preference_router.py`, `tests/api/test_preferences_route.py`

## 2. 참여자별 만족도와 공정성 점수

### 문제

여러 사람의 선호를 하나의 목록으로 합치면 "누구의 선호인지"가 사라져, 세 명 중 두 명은 매우 좋아하고 한 명은 전혀 만족 못 하는 후보와 세 명 모두 적당히 만족하는 후보를 구분할 수 없다. `/candidates` 요청엔 이미 `participants[].userId`로 참여자 구분이 들어오는데, 과거엔 라우트에서 이걸 하나의 배열로 평탄화해서 버리고 있었다.

### 검토한 방식과 선택

| 방식 | 한계 |
| --- | --- |
| 선호를 합쳐 LLM이 순위 결정 | 계산 근거가 사라지고 호출마다 순위가 흔들릴 수 있음 |
| 개인 만족도의 단순 평균 | 여러 명의 높은 점수가 한 명의 매우 낮은 만족도를 가릴 수 있음 |
| 최저 만족도만 최대화 | 한 명의 약한 선호가 전체 선택을 지나치게 보수적으로 만듦 |
| **평균 70% + 최저 30% + 알레르기 veto(채택)** | 가중치·정의가 서비스 정책이며 실데이터로 조정 필요 |

**Back 요청/응답 스키마는 바꾸지 않았다.** `participants[].userId`/`preferences[]`가 이미 있으므로, AI 내부에서 이 구조를 평탄화하지 않고 후보 평가까지 보존하도록 그래프 상태와 라우트만 바꿨다. 응답에도 `fairnessScore` 같은 새 필드를 추가하지 않고, 계산 결과는 기존 `suggestions[].rank`를 정하는 내부 근거로만 쓴다.

### 핵심 메커니즘

1. **목적 적합성 gate** — 후보가 모임 목적과 관련 있는지 `contextRelation: DIRECT/PARTIAL/NONE`을 LLM이 판정. `NONE`은 공정성 점수에 섞지 않고 **영업 검증 전에 hard gate로 제외**한다(선호 점수로 목적 위반을 상쇄하지 않음).
2. **선호 관계 판정** — 남은 후보에서 LLM이 후보-선호 관계를 `DIRECT(1.0)/PARTIAL(0.5)/NONE(0.0)`로만 판정한다. 숫자·순위는 LLM이 만들지 않는다. 최대 15개 후보를 5개씩 최대 3 batch로 나눠 병렬 평가하고, 서버가 후보 ID·참여자 ID·선호 코드가 전부 입력과 일치하는지 검증한다(하나라도 어긋나면 `502 MODEL_RESPONSE_INVALID`).
3. **점수 계산(순수 코드)**:

```
q(i,p,c) = 0.5 + 0.5 × d(p) × m(i,p,c)     d: POSITIVE=+1, NEGATIVE=-1
u(i,c)   = Σ[w(p)×q(i,p,c)] / Σw(p)         w: WEAK=1, MODERATE=2, STRONG=3
S(c)     = 평균 u(i,c)      F(c) = 최저 u(i,c)
Score(c) = 100 × (0.7×S(c) + 0.3×F(c))
```

선호 없는 참여자는 중립값 `u=0.5`. 예시: `[1.0, 1.0, 0.0]`(한 명 소외) → 46.7점, `[0.6, 0.6, 0.6]`(고르게 만족) → 60.0점 — 단순 평균이면 전자가 높지만 최저 만족도를 반영하면 후자가 앞선다.

4. **알레르기만 별도 veto** — 일반적인 `STRONG+NEGATIVE`는 veto하지 않고 만족도 `0.0`까지만 반영한다. `_ALLERGY` 코드가 후보와 `DIRECT`로 충돌할 때만 점수 경쟁 전에 강제 제외한다.
5. **정렬** — `Score → F → S → contextRelation(DIRECT 우선) → 원래 Kakao 순서`.

이 사전랭킹 순서대로 영업 검증(3장)을 진행하고, 최종 응답은 기존 `suggestions[].rank/reasons/tags` 형식 그대로 나간다.

### 한계

- `0.7/0.3`, 강도 가중치 `1/2/3`은 학습된 최적값이 아니라 서비스가 정한 초기 정책이다.
- 최종 집계는 결정론적이지만 `DIRECT/PARTIAL/NONE` 판정 자체는 여전히 LLM 몫이다 — "전체가 수학 계산"이 아니라 "의미 판정 결과를 결정론적 공식으로 집계하는 구조"라고 표현해야 정확하다.
- Kakao 장소명·카테고리만으로 실제 재료·교차오염까지 확인할 수 없어 알레르기 안전을 완전히 보증하지 않는다.
- `contextRelation=NONE` hard gate가 오판하면 좋은 후보가 검증 전에 사라지는 false negative가 생길 수 있다.
- 참여자·선호 수가 커지면 LLM이 반환해야 하는 관계 행렬 크기도 커진다 — batching은 지연을 줄이지만 총 출력량 자체를 없애진 않는다.

### 코드 근거

- 참여자별 요청 스키마: `app/schemas/candidates.py`
- 참여자 구조를 보존하는 라우트: `app/api/routes/meetings.py`

## 3. 웹 검색 기반 영업시간 검증

### 문제

Kakao Local API로는 장소 ID·상호명·주소·카테고리·좌표까지는 안정적으로 얻지만, 확정된 모임 날짜·시간에 실제로 영업하는지는 알 수 없다(정기휴무, 임시휴무, 모임 도중 영업 종료 등). 그렇다고 최대 15개 후보를 전부 웹 검증하면 비용·지연이 커진다.

### 검토한 방식과 선택

| 방식 | 한계 |
| --- | --- |
| Kakao 정보만 사용 | 특정 시간대 영업 여부 정보가 없음 |
| Gemini `google_search` grounding으로 검색+판정 | 일반 생성 호출과 별도의 빡빡한 할당량으로 실제 실행에서 `429`가 자주 발생 |
| 검색 스니펫을 규칙으로만 파싱 | 요일·공휴일·브레이크타임 표현이 다양해 규칙이 빠르게 복잡해짐 |
| 후보 전체(최대 15개) 웹 검증 | 후보마다 검색+판정 호출이 필요해 비용·지연이 불필요하게 커짐 |
| **공정성 상위 6개 우선 검증 + 부족 시 3개씩 확장(채택)** | usable이 계속 부족하면 결국 15개까지 검증해 절약 폭이 줄어듦 |

초기엔 Gemini `google_search` grounding을 썼지만 재시도에만 35초가 걸려 20초 전체 타임아웃 안에서 에러 로그도 없이 실패하는 문제가 있었다(할당량 초과가 타임아웃처럼 보임). **검색(Serper)과 판정(Gemini)을 분리**해 해결했다.

### 핵심 메커니즘

역할 분리:

| 구성 요소 | 담당 |
| --- | --- |
| Kakao Local API | 후보 풀 최대 15개 구성 (영업 여부는 판정 안 함) |
| Fairness Pre-Ranker | gate·공정성으로 검증 우선순위 결정 |
| Serper API | 장소명+주소로 검색해 제목·스니펫·URL 수집 (의미 해석 안 함) |
| Gemini | 검색 근거와 모임 시간을 비교해 `PASS/FAIL/UNKNOWN` 구조화 판정 (직접 검색 안 함) |
| 서버 코드 | batch 제어, timeout, 근거 정규화, 최종 태그 부착 |

검색어는 LLM이 아니라 코드 고정 템플릿: `{place_name} {address} 영업시간 휴무일`. Gemini에는 확정 날짜·시작/종료 시각(Asia/Seoul로 변환)과 검색 결과만 전달한다. 서버는 Gemini가 반환한 `source`가 실제 검색 결과 URL 중 하나인지 대조하고, `PASS`인데 근거(출처/영업시간)가 부족하면 `UNKNOWN`으로 강등한다.

**Boolean이 아니라 3-state**:

| 상태 | 의미 | usable | 최종 응답 |
| --- | --- | --- | --- |
| `PASS` | 모임 시간 전체가 영업시간 안에 포함 | 예 | `businessHoursVerified=true`, 이용 가능 태그 |
| `FAIL` | 휴무·폐업 또는 시간대 벗어남 | 아니오 | 최종 후보에서 제외 |
| `UNKNOWN` | 정보 부족/충돌/오류/timeout | 예 | `businessHoursVerified=false`, 태그 없음 |

"확인 못 함"과 "확인했더니 닫음"은 다른 상태라서 `UNKNOWN`도 후보는 보존하되 확인된 것처럼 표시하지 않는다.

**단계적 검증**: 사전랭킹 상위 6개를 먼저 병렬 검증하고, usable(`PASS`+`UNKNOWN`)이 3개 미만이면 다음 3개씩 반복 확장한다. 모든 batch가 공통 20초 deadline을 공유한다(각 batch가 새로 20초를 받지 않음). 정책 한 문장: **"후보 보존에는 fail-soft, '영업한다'는 사실 주장에는 fail-closed."** 검색 실패·timeout은 후보를 지우지 않고 `UNKNOWN`으로 보존하지만, `PASS`가 아니면 이용 가능 태그를 붙이지 않는다.

최종적으로 비-LLM Suggestion Builder가 `FAIL`을 제외하고 usable을 사전랭킹 순서대로 최대 3개 조립한다. Back 응답 스키마는 그대로다 — `PASS/UNKNOWN/FAIL`은 AI 내부 상태이고, 밖으로는 기존 `businessHoursVerified`/`openAtMeetingTime`/태그로만 나간다.

### 한계

- 검색 결과가 공식 최신 정보라는 보장은 없다 — "실시간 검증"이 아니라 "검색 시점의 웹 근거 기반 검증"이 정확한 표현이다.
- Serper `organic` 상위 5개 제목·스니펫만 쓰고 knowledge graph/places 같은 구조화 정보는 아직 안 쓴다.
- 같은 상호명의 다른 지점이 섞일 위험이 있다(주소를 검색어에 포함해 완화만 함).
- 출처 URL이 실제 검색 결과에 있다는 것만 검증하지, 그 출처가 공식/최신이라는 것까진 보증 못 한다.
- 브레이크타임·라스트오더·자정 넘김 같은 복잡한 영업시간은 여전히 LLM 해석에 의존한다.
- 재시도·캐시 정책이 없어 같은 장소를 매번 새로 검색한다.
- `6`/`3`/`20초`는 학습으로 최적화한 값이 아니라 초기 정책이며, `FAIL`이 계속되면 결국 15개 전부 검증할 수도 있어 항상 호출이 줄어드는 건 아니다.

## 4. 발표에서 실제로 받은 질문

### 4.1 카카오맵 API의 오래되거나 잘못된 정보를 LLM에 보내기 전에 걸러내는가

**아니다.** `app/services/kakao_client.py`는 Kakao 응답을 그대로 파싱해서 넘긴다. 폐업 여부나 정보 최신성을 판별하는 전처리가 없다. 유일한 사실 검증은 3장의 **영업시간 전용** 검증뿐이라, 주소·카테고리 오류 같은 문제는 걸러지지 않고 그대로 Ranker까지 전달된다. 실제 한계로 인정해야 한다.

### 4.2 네이버지도가 정보가 더 많은데 왜 카카오맵 API를 선택했는가

실제 팀 결정 근거가 저장소 기록에 남아있지 않다. 일반적으로 알려진 이유(개인/소규모 프로젝트 기준 발급·무료 할당량 접근 용이, REST API 문서화)는 있지만 실제 선택 이유였는지는 확인이 필요하다.

### 4.3 개인 선호도 입력에 AI를 쓰는 게 오버엔지니어링 아닌가

1장의 트레이드오프가 답이다. 드롭다운으로도 선호는 받을 수 있지만 사전에 없는 표현이나 복합·반대 선호를 표현할 수 없다. 자연어 입력은 표현력을 얻는 대신 매핑 정확도·프롬프트 비용이라는 대가를 지불하는 선택이다.

### 4.4 앱 설치·초대·모임 생성 자체도 시간이 걸리는 일 아닌가 / 굳이 이 서비스를 써야 하나 / 초대 과정이 복잡해 진입장벽이 높다

세 질문 모두 초기 설정 비용 문제다. 타깃을 "1회성 모임이 아니라 여러 해 이어지는 **정기 모임**"으로 좁힌 이유가 답이다 — 초기 비용(설치·초대·선호 입력)은 첫 모임에서 한 번만 지불하고 같은 그룹이 반복 모일 때마다 상각된다는 논리다. 다만 검증된 사실이 아니라 제품 가설이며, 실제로 상각될 만큼 재사용 빈도가 나오는지는 별도 검증이 필요하다. 초대·가입 복잡성은 다자간 조율 서비스 전반의 콜드스타트 문제이지 다모여만의 결함은 아니지만, 문제가 없다는 뜻도 아니다.
